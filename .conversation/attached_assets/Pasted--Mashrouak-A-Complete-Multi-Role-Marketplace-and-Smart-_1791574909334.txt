# Mashrouak (مشروعك) — A Complete Multi-Role Marketplace and Smart Delivery Web App

Build a complete, modern, professional, responsive web application called **Mashrouak | مشروعك**.

Mashrouak is a Jordanian marketplace platform that connects small businesses and independent project owners with customers, while allowing delivery couriers to discover nearby delivery requests, accept orders, contact customers, and complete deliveries.

The platform has three main user roles:

1. **Customer:** Discovers projects and shops, browses products, adds products to a cart, places orders, shares a delivery location, and tracks order status.
2. **Project Owner / Merchant:** Creates and manages a project storefront, adds products, manages inventory, receives customer orders, and tracks sales and delivery progress.
3. **Delivery Courier:** Views nearby delivery requests, checks pickup and drop-off locations, accepts deliveries, obtains the necessary customer contact details, and updates delivery status.

The application must feel like a real, fully designed marketplace combined with a professional merchant dashboard and a smart delivery system.

Build the actual multi-page application, not just a landing page or static dashboard. Prioritize a beautiful interface, functional interactions, realistic demo data, and clear navigation between all user experiences.

## 1. Technology and Implementation

Use:

* React and Vite.
* JavaScript and JSX.
* Tailwind CSS.
* React Router for navigation.
* Lucide React for icons.
* Recharts for charts.
* React Leaflet with OpenStreetMap for interactive maps.
* Centralized mock data and reusable components.
* Local storage for demo persistence.
* Context or another lightweight state management approach for cart, language, theme, and current demo user.

Do not require paid API keys or paid services.

Use mock authentication and role selection for the hackathon demo. Clearly separate the demo authentication layer from the UI so it can later be replaced with real authentication.

Keep the frontend ready for integration with an existing Python backend, database models, and a real delivery optimization service. Do not invent a second backend or replace existing backend code if one is already provided.

### Accepting a Delivery

When the courier accepts a request:

1. Verify that the order is eligible for delivery.
2. Assign the delivery to the selected demo courier.
3. Change the request status so it is no longer available to other couriers.
4. Add the delivery to the courier's active deliveries.
5. Update the merchant's order page.
6. Update the customer's order tracking page.
7. Show a success notification.

Prevent two demo couriers from accepting the same request within the application's shared state.

If the order is not yet ready for pickup, show its preparation status and do not allow an invalid pickup action.

### Customer Contact Information

After a courier accepts a delivery, show the information required to complete that delivery:

* Customer name.
* Customer phone number supplied during checkout.
* Delivery address.
* Map coordinates when available.
* Delivery instructions.
* Order reference.

Show pickup contact information for the merchant when needed.

Keep this information hidden from couriers who have not accepted the delivery. Do not expose customer information publicly or in unrelated delivery requests.

Add click-to-call and contact actions using the available phone number, with sensible fallbacks when the demo has no number.

### Active Delivery Workflow

Provide a dedicated active delivery details page.

The courier should be able to update the delivery through valid stages:

* Accepted.
* Heading to pickup.
* Picked up.
* On the way to customer.
* Delivered.

Require a confirmation before marking an order as delivered.

After completion:

* Update the order status.
* Remove the delivery from the available requests.
* Move it to delivery history.
* Update customer tracking.
* Update merchant order status.
* Display a delivery-completed confirmation.

Allow a courier to decline or release an accepted delivery only through a controlled action with an appropriate status update.

Do not implement real GPS tracking, real phone verification, or real-time notifications unless the relevant service is connected. Simulate these interactions clearly in demo mode.

## 9. Shared Order and Delivery Lifecycle

The application must use a consistent order lifecycle across all three roles.

A customer's order should be created once and referenced by:

* The customer.
* The merchant.
* The courier after assignment.
* The smart delivery module when eligible.

All relevant screens should reflect status updates from the same shared demo state.

For example:

* Customer places an order.
* Merchant confirms and prepares it.
* Merchant marks it ready for pickup.
* The request becomes available to couriers.
* A courier accepts it.
* Customer and merchant see the courier assignment.
* Courier picks up and delivers the order.
* All relevant dashboards show the final delivered status.

Implement this flow with centralized state and local storage for the hackathon demo. Do not maintain unrelated copies of the same order in separate pages.

Include sensible validation and prevent invalid status transitions.
